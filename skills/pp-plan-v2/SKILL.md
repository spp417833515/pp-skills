# /pp-plan-v2 — 基于上下文的最终方案制定

## 定位

```
不是从零问需求 · 是把对话上下文沉淀为可执行的最终方案文档
不是只产新代码方案 · 也能产 "优化 / 清理 / 审查方案" 类产出
不是缝缝补补保留兼容 · 有问题代码直接清理+重建
```

## 调用方式

```
/pp-plan-v2              读当前对话上下文 + clarify 锁定的三件产物 · 自动提炼任务名
/pp-plan-v2 <任务名>     显式指定目录名
```

上下文为空 / 无可提炼决策 → 提示用户先沟通 · 不强进。
无 clarify lock 的三件产物,且对话里也无等价「目的+非目标+代码层授权」→ 提示先 /pp-clarify-v2 · 不强进(三段闸门 ①→②)。

## 接口契约(移植先看这 · 三段式见 /pp-pipeline §五)

| 项 | 内容 |
|---|---|
| 输入 | 对话上下文 + clarify 三件产物(记账① 读取;离线模式读 `任务目录/澄清.md`) |
| 输出 | `.pp/wiki/当前任务/[任务名]/` 下 3 份 MD(目录已由 clarify 创建,缺则本技能补建) |
| Store 接线 | ppwiki `clarify --get` / `--derive_task` · 记账①② → 见 §Store 接线 |
| 缺依赖行为 | 无三件产物且对话无等价物 → 不强进;无 ppwiki → 读本地澄清.md · 跳过派生(声明) |

## 开发中项目铁律(贯穿全程)

```
代码 / 逻辑 / 数据有问题  →  直接清理干净 + 构建正确的
禁止: 缝缝补补 / 兼容旧版 / 保留错误链路 / try-except 吞错
理由: 缝补 = 潜在错误 = 长期翻倍还债
```

任何违反 → 方案作废 · 重做。

## 输出强制要求

最终产物 = `.pp/wiki/当前任务/[任务名]/` 下 **3 份 MD · 缺一不可**:

```
.pp/wiki/当前任务/[任务名]/
├── 对话和澄清.md       对话沉淀 + AI 理解 + 决策记录
├── 验收标准.md         攻击性验收(找漏洞视角)
└── 执行方案.md         五类产出清单(复用/优化/修改/清理/新建)
```

**自审报告不落盘**(内部门槛 · 不输出过程)。

## 一、三文档硬性内容契约

### 对话和澄清.md(沉淀 · 不再问)

| 章节 | 必含 |
|---|---|
| §1 | 用户对话原话(关键回合摘录 · 直引不重写)|
| §2 | AI 对话理解(每段原话 · AI 的解读)|
| §3 | 已锁定决策(候选 → 选定 → 理由 · MD 表)|
| §4 | 未决决策(待用户拍板的 · 列候选 + 推荐)|
| §5 | 用户感知效果(完成后用户能看到什么 · 代码示例 + 条件清单)|

### 验收标准.md(攻击性 · hostile reviewer 视角)

| 章节 | 必含 |
|---|---|
| §1 | **代码风格冲突**(违反 项目公约 AGENT.md 红线 1-8 / 三层架构 / **缝缝补补红线** / 一行调用 · 职责单一 · 体量上限>200行拆)|
| §2 | **冲突数据**(改后是否与现有数据格式 / 字段语义冲突 · 列字段对照表)|
| §3 | **冲突逻辑**(改后是否破坏现有调用链 / 副作用 / 跨模块约束)|
| §4 | **重复造轮子**(检索过项目 + 生态 · 证明无现成可复用 · 列搜索路径)|
| §5 | **命令式验收**(每条 = 可执行命令 + 精确期望值 · 禁含糊词)|
| §6 | **真实链路测试**(≥ 1 条真实 URL/KEY · 不是纯 mock)|
| §7 | **退出标准**(全部 must 才放行)|

### 执行方案.md(五类产出清单)

| 章节 | 必含 |
|---|---|
| §0 | 顶部铁律("开发中项目禁缝缝补补" · 复述给执行者)|
| §0.0 | **逻辑流程图定位**(三件套:① 全局逻辑流程图 mermaid · 节点=抽象逻辑动词非文件名 · 来源 wiki `_README` 沉淀图 + 证据/代码证据.md(clarify 三源所得 · 缺则自读代码并声明);② 任务节点标记:改节点内部 还是 节点间契约;③ 上下游影响表:关联节点/方向/契约变?/影响/处置 · 契约不变=传播截断,变=沿边推下一跳)|
| §0.1 | **架构改前/改后**(ASCII 图)+ 架构3问(能承载?最简路径?能长期用?)· 任一否→先改架构 |
| §0.2 | **底层探测表**(动词→底层能力 ❌缺/✅有)· 缺→子任务首项"补底层 X"(底层先足量)|
| §0.3 | **子任务分层表**(序号/子任务/所属层/涉及文件/依赖谁;≥2 模块协作另列模块契约表)+ 污染自查3问(跨≥2层?标不清层?UI↔Store 直连 / UI→逻辑层 做业务直跳?)|
| §0.4 | **影响范围清单**(由 §0.0 上下游影响表推导 · 每条标来源节点/边 · 影响文件/模块/功能 · 确认不误伤无关功能)|
| §1 | **复用清单**(已有可直接调用的能力 · 每条 file:line)|
| §2 | **优化清单**(已有代码 · 可重构得更干净 · file:line + 优化点)|
| §3 | **修改清单**(现有代码必要改动 · file:line + 改动要点)|
| §4 | **清理清单**(错误 / 冗余代码 · 直接删 · file:line + 删除理由)|
| §5 | **新建清单**(确实缺的能力 · 预定路径 + 函数签名)|
| §6 | 调用链图(mermaid · 串起 §1-§5 各项)|
| §7 | 执行顺序(底层 → 业务 → 用户层 · 复用优先)|
| §8 | 风险与取舍(4 字段:触发 / 影响 / 缓解 / 决策)|
| §9 | 完成定义(含真实链路硬条件 + 物证)|

## 二、产出类型可灵活配比

```
新功能任务      → §1+§3+§5 主力(复用 + 修改 + 新建)
重构任务        → §2+§4 主力(优化 + 清理)
审查/优化方案   → 不一定出 §5(可全无新代码 · 只给优化建议)
Bug 根治        → §3+§4 主力(修根因 + 清理绕行)

§ 全空不允许 · 至少有一类产出
```

## 三、内部自审 12 项(门槛 · 不落盘)

切到"审查者"角色 · 第一性原理过 12 项:

| # | 自审项 | 通过标志 |
|---|---|---|
| 1 | 对话理解一致 | AI §2 理解 ↔ 用户原话 §1 对得上 · 无臆测 |
| 2 | 决策点齐全 | 对话所有决策都落 §3 · 未决都落 §4 |
| 3 | 攻击性 4 维都查过 | 代码风格 / 数据 / 逻辑 / 重复造轮子 各一节 |
| 4 | **产出优先级** | 复用 > 优化 > 修改 > 清理 > 新建 · 跳级必证不可 |
| 5 | 改动都带证据 | §1-§4 file:line · §5 预定路径 + 签名 |
| 6 | 真实链路 ≠ 纯 mock | ≥ 1 条真实 URL/KEY |
| 7 | **禁缝缝补补** | 有问题代码必入 §4 清理 · 非 fallback / 兼容 / 双链路 |
| 8 | **架构合理** | §0.1 改前/改后图 + 架构3问 全过 · 不是带病加功能 |
| 9 | **分层无污染** | §0.3 分层表无跨≥2层 · 无 UI↔Store 直连 / UI→逻辑层 做业务直跳 · 污染3问全否 |
| 10 | **底层探测齐** | §0.2 动词→底层 ❌缺/✅有 表在 · 缺→子任务首项"补底层 X"(底层先足量) |
| 11 | **影响范围齐** | §0.4 清单在 · 每条可溯源到 §0.0 节点/边 · 确认不误伤无关功能 |
| 12 | **逻辑定位齐** | §0.0 三件套在(全局图/任务节点标记/上下游影响表)· 每个相邻节点有契约判定 |

任一项不通过 → 内部回写对应 MD → 再自审 · 循环 ≤ 3 轮。
3 轮仍有缺口 → 暂停 · 列缺口给用户 · **不强出方案**。

**12 项过后 · 子代理模拟验证(对抗自审升级 · 用 Agent 工具派子代理)**:
```
派 subagent 扮 hostile executor · 拿 执行方案.md 模拟跑一遍 · 专挑漏洞:
  · 复用清单 §1 的 file:line 真存在?函数签名对得上?(不存在 = 跳级新建伪装)
  · §0.0 全局流程图是真的吗?节点/边有代码证据吗?有没有漏画的上游/下游节点?
  · 验收命令 §5 真能跑?期望值现实?真实链路 §6 的 URL/KEY 可达?
  · 五类产出执行顺序 §7 会不会依赖倒置卡死?
  · 藏着缝缝补补 / 双信源 / try-except 吞错 / fallback?
子代理产「攻击报告」→ 命中缺口回写对应 MD → 再过 12 自审 · 循环 ≤ 2 轮。
```
全部通过 + 子代理无致命攻击 → 一次性写最终 3 份 MD。

## 四、违规项(红线 · 命中即作废)

| # | 违规 | 判定 |
|---|---|---|
| 1 | 缝缝补补 | 现存错误代码未入 §4 清理 · 改用 fallback / 兼容 / 双链路 |
| 2 | 结论不带 file:line | §1-§4 任一条没源码定位 = 猜测 |
| 3 | 重复造轮子 | §5 新建但未在 §4(攻击性验收)证明无可复用 |
| 4 | 验收含糊 | "应该 / 大概 / 通常" / 无可执行命令 + 期望值 |
| 5 | 跳级新建 | 跳过 §1 复用 / §2 优化 / §3 修改 直接 §5 新建无理由 |
| 6 | 3 份 MD 不齐 | 缺任何一份 |
| 7 | 自审未过即输出 | 12 项内部门槛未过即写最终 MD(自审=门槛·未过回写;违规=作废·仍输出即作废)|
| 8 | 决策臆测 | §3 决策不来自对话原话 · 是 AI 猜的 |

## Store 接线(ppwiki · 移植时改写/删除本节 · 方法论正文零 ppwiki)

| 记账点 | 时机 | op |
|---|---|---|
| ① | 启动 · 读三件产物 | `clarify --get {name}`(name=null 取最新 active) |
| ② | 读毕 · 派生任务 | `clarify --derive_task {name, priority}`(澄清快照入 task · 物理删原澄清 · **task 由此诞生**,所有权 → /pp-pipeline §三) |

- op / 参数以 `ppwiki('system --help', {module:'clarify'})` 为准 · 禁凭记忆
- 离线降级:① 改读 `任务目录/澄清.md`;② 跳过并显式声明「task 未派生」· 禁静默

## 六、契约

```
上游:clarify 三件产物 + 证据/{代码证据,外部证据}.md
产出:3 份 MD(对话和澄清 / 验收标准 / 执行方案)+ 派生 task

```
